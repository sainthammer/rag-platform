
Параметры **`DEFERRED`** и **`IMMEDIATE`** в SQL используются для управления моментом проверки ограничений (constraints) на уровне транзакций, в частности — уникальных индексов и внешних ключей (foreign keys). Эти параметры управляют, когда именно будет происходить проверка ограничений: немедленно (сразу после выполнения команды) или отложено (в конце транзакции).

### Как работают `DEFERRED` и `IMMEDIATE`:

- **`IMMEDIATE`**: Ограничение проверяется **сразу** после выполнения команды. Если ограничение нарушено, ошибка возникает немедленно, и команда откатывается. Это поведение по умолчанию для большинства ограничений.

- **`DEFERRED`**: Ограничение проверяется только **в конце транзакции**, то есть при выполнении команды `COMMIT`. Это позволяет временно нарушить ограничение в середине транзакции, а затем исправить это до её завершения.

### Контекст использования в индексах

Эти параметры обычно применяются к **уникальным индексам** или ограничениям на уровне целостности данных (например, внешние ключи), а не непосредственно к самому индексу, но индексы могут быть связаны с ограничениями. Например, уникальные индексы используются для реализации уникальных ограничений.

#### Пример синтаксиса при создании ограничения:

```SQL

CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE INITIALLY IMMEDIATE
);

```

В этом примере `UNIQUE` означает, что значение в колонке `email` должно быть уникальным, и оно будет проверяться **немедленно** (по умолчанию). Можно явно указать `INITIALLY IMMEDIATE`, но это поведение по умолчанию, если параметр не указан.

А если вам нужно временно откладывать проверку уникальности, используйте `DEFERRED`:

```SQL

CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE INITIALLY DEFERRED
);

```

Теперь ограничение будет проверяться только в момент завершения транзакции.

### Детали работы `DEFERRED` и `IMMEDIATE`:

1. **IMMEDIATE (немедленная проверка)**:
    
    - Ограничения проверяются сразу после каждой команды, модифицирующей данные (например, `INSERT`, `UPDATE`).
    - Если ограничение нарушено, операция сразу завершится ошибкой.
    - Например, если вы пытаетесь вставить строку с дублирующимся значением в поле, которое должно быть уникальным (например, email), ошибка возникнет сразу при выполнении команды `INSERT`.

1. **DEFERRED (отложенная проверка)**:
    
    - Ограничения проверяются только в конце транзакции, на этапе выполнения команды `COMMIT`.
    - Вы можете временно вставить или обновить данные, которые нарушают ограничение, и затем в рамках той же транзакции привести их в соответствие до завершения транзакции.
    - Если по завершении транзакции (при `COMMIT`) данные по-прежнему нарушают ограничение, то произойдёт ошибка, и вся транзакция будет отменена.

#### Пример использования в транзакциях:

Допустим, у вас есть таблица `accounts` с ограничением уникальности на колонку `account_number`:

```SQL

CREATE TABLE accounts (
    id SERIAL PRIMARY KEY,
    account_number VARCHAR(50) UNIQUE INITIALLY DEFERRED
);

```

Теперь, если вы выполняете такую транзакцию:

```SQL

BEGIN;

UPDATE accounts SET account_number = '12345' WHERE id = 1;
UPDATE accounts SET account_number = '12345' WHERE id = 2;

COMMIT;

```

При использовании `IMMEDIATE` ограничение на уникальность будет проверено сразу при выполнении каждой команды `UPDATE`, и вторая команда вызовет ошибку, потому что она нарушает уникальность.

Однако с `DEFERRED` обе команды будут выполнены, но ограничение будет проверено только при выполнении `COMMIT`. Если на момент завершения транзакции уникальность нарушена, вся транзакция будет отменена, и изменения не будут сохранены.

### Когда использовать `DEFERRED` и `IMMEDIATE`:

1. **`IMMEDIATE`** — используется, когда нужно немедленно проверять целостность данных после каждой операции. Это стандартное поведение, которое предотвращает временное нарушение ограничений и требует, чтобы данные были корректными на каждом шаге.
    
    - Применяется в большинстве случаев, когда нарушения целостности данных недопустимы даже временно.
    - Например, в сценариях, где несколько команд не должны нарушать уникальные или внешние ключи.

1. **`DEFERRED`** — полезен, когда в рамках одной транзакции могут временно нарушаться ограничения, но в конечном итоге данные будут скорректированы до её завершения.
    
    - Это полезно, например, при циклических внешних ключах (когда два объекта ссылаются друг на друга через внешние ключи).
    - Также может применяться при обновлении нескольких строк, которые временно нарушают уникальность, но будут исправлены до завершения транзакции.

### Пример использования:

Предположим, у вас есть таблицы `orders` и `customers`, связанные через внешний ключ. Если вам нужно переместить записи между ними, вы можете использовать `DEFERRED`, чтобы временно нарушить это ограничение, пока не завершите перемещение всех связанных данных:

```SQL

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    customer_id INT REFERENCES customers(id) DEFERRABLE INITIALLY DEFERRED
);

```

Здесь внешний ключ `customer_id` откладывает проверку до конца транзакции.

Пример транзакции:

```SQL

BEGIN;

UPDATE orders SET customer_id = NULL WHERE customer_id = 1;
DELETE FROM customers WHERE id = 1;

COMMIT;

```

В режиме `DEFERRED` эта последовательность команд будет успешно выполнена, так как ограничение внешнего ключа будет проверено только при `COMMIT`. В режиме `IMMEDIATE`, наоборот, проверка произошла бы после первой команды, и она завершилась бы ошибкой.

### Заключение:

- **`IMMEDIATE`** проверяет ограничения сразу после каждой операции. Это поведение по умолчанию, которое гарантирует, что данные остаются корректными на каждом этапе выполнения команд.
- **`DEFERRED`** откладывает проверку ограничений до конца транзакции, что позволяет временно нарушить ограничения в середине транзакции и исправить данные до её завершения.

Эти параметры полезны для управления целостностью данных и дают гибкость при сложных операциях, где данные могут временно нарушать ограничения, но будут исправлены до завершения транзакции.
