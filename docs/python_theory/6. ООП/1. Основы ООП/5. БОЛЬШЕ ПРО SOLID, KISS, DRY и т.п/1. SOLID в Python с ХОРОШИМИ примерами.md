# S olid - Single responsibility (единая ответственность)

### Суть принципа

Один класс/метод по возможности отвечает за что-то одно.

### Что будет если нарушить?

Вам будет очень сложно расширять программу/модифицировать код, потому что у вас будет плохая сегрегация зон ответственности в коде. По сути у вас будет множество причин, почему ОДНУ штуку, нужно менять ПО МНОЖЕСТВУ причин. В конечном итоге такой код просто станет сложным для понимания. В нем надо будет РЕАЛЬНО КОПАТЬСЯ, просто для того, чтобы понять, а что тут происходит.

### Пример нарушения:

Пусть мы хотим сделать систему отправки пользователю уведомлений о каких-то событиях в нашем приложении. Изначально мы просто создаем класс, где разные методы отвечают за разные способы отправки:

```python

class UserNotification:  
    def notify_by_email(self):  
        """Данный метод отправляет уведомление на E-mail."""  
        # Логика отправки сообщения на электронную почту пользователя.  
        pass  
    def notify_by_push(self):  
        """Данный метод отправляет push уведомление в приложение."""  
        # Логика отправки push уведомление в наше приложение.  
        pass  
    def notify_by_sms_message(self):  
        """Данный метод отправляет sms пользователю."""  
        # Логика отправки sms сообщение  пользователю.  
        pass

```

В данном примере, проблема в том, что у нас не очень удачное название методов, как минимум, а ещё при изменении любого из способов отправки уведомлений, мы полезем в этот класс, если у нас будет ещё 10 способов доставки сообщений (В ТГ, WhatsApp ...), то класс будет разрастаться. А это мы только начали накидывать логику.

### Пример исправления:

Нам нужна такая система, которая будет использовать принципы ООП наследование и полиморфизм. Мы разделим каждый способ отправки сообщений на отдельный класс и объединим их одной абстракцией, чтобы было понятно, что все они занимаются отправкой уведомлений, но реализуют разные способы:

```python

from abc import ABC, abstractmethod


class Notification(ABC):
    @abstractmethod
    def send_notification(self, massage: str) -> None:
        """Метод будет отвечать за отправку пользователю уведомления."""
        # Будет какая-то логика отправки massage
        raise NotImplementedError("Это класс не должен инициализироваться.")
    
    
class EmailNotification(Notification):
    """Класс для отправки уведомлений по E-mail'у."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки уведомлений по E-mail'у."""
        # Логика отправки massage по E-mail
        pass
    
    
class PushNotification(Notification):
    """Класс для отправки push уведомлений в приложение."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки push уведомлений в приложение."""
        # Логика отправки massage d push уведомление
        pass
    
    
class SMSNotification(Notification):
    """Класс для отправки sms пользователю."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки sms пользователю."""
        # Логика отправки sms пользователю
        pass

```

**Почему так лучше:** даже если в каждый класс будут добавляться какие-то свои методы, которые будут вызываться в  методе send_notification(), это будет в одной области для программиста, в одном классе, который отвечает, например, за отправку push уведомления. А ещё теперь у всех способов отправки уведомления есть 1 метод send_notification(), что в будущем позволит их легко взаимно заменять при необходимости.

# s O lid - open/close (принцип открытости/закрытости)

### Суть принципа

Классы и методы, которые УЖЕ где-то используются, вызываются и активно эксплуатируются в коде нельзя просто брать и менять. Нужно создавать наследников от этого класса, чтобы ничего случайно не сломать

### Что будет если нарушить?

Старый уже работавший код будет ломаться, и будет очень сложно добиться того, что работает и новое и старое. Код получиться очень сложный и плохо масштабируемый.



### Пример нарушения:

Давайте представим, что наш класс отправки уведомлений в E-mail отлично работал все это время. приложения разрослось логикой, оправка уведомлений используется для множества событий и т.п. НО в один прекрасный момент мы добавляем поддержку какого-то не очень стандартного E-mail сервиса/ Так вот если по примеру выше мы сразу пойдем менять класс EmailNotification, то с довольно высокой вероятностью мы можем что-то сломать, где он уже использовался. Нам будет тяжело добавить поддержку нового Email сервиса так, чтобы и он нормально работал и со старым функционалом, и чтобы новое "завелось" нормально. И да... Давайте представим, что через неделю у нас поставили задачу прикрутить поддержку другого Email сервиса. который тоже работает по-другому. Короче в коде будет жопа.

В данном примере, проблема в том, что при добавлении ещё одного специфического случая, придется все усложнять код и дальше, причем не факт, что на реальном примере мы обойдемся просто конструкцией if...elif...else

### Пример исправления:

Нам нужна такая система, которая будет использовать принципы ООП наследование и полиморфизм. Мы создадим несколько наследников для EmailNotification, которые уже будут реализовывать логику каждый для своего особого сервиса

Почему так лучше: мы можем теперь хоть миллион классов для каждого Email сервиса добавить, то что уже использует готовые классы не сломается, а новые отдельно существуют и потихоньку встраиваются в проект. Все довольны, легко масштабируется и работает.

# so L id - Liskov Substitution (**Принцип подстановки Барбары Лисков**)

### Суть принципа

Классы наследники должны заменять своих родителей в коде без ошибок или получения не того результата, что мы ожидаем.

### Что будет если нарушить?

Будет нарушена логика семейства классов, то есть у нас как бы на каком-то поколении появляются "неправильные" дети, которых в коде нельзя подставить на место родителя и ожидать, что программа работает правильно. Т.е. разработчику, который плохо знаком с вашей архитектурой приложения будет очень сложно копаться, выяснять, где в каких случая с какими объектами каких классов что-то ломается. Такое приложение будет сложно поддерживать

### Пример нарушения:

В предыдущем примере я как раз НАРУШИЛ этот принцип. Дело в том, что если мы подставим объект моего класса EmailNotificationMyMail вместо EmailNotification и будем использовать его для обычных Email сайтов, то отправка уведомлений не отработает корректно, либо что-то вообще выдаст ошибку.

```python

from abc import ABC, abstractmethod


class Notification(ABC):
    @abstractmethod
    def send_notification(self, massage: str) -> None:
        """Метод будет отвечать за отправку пользователю уведомления."""
        # Будет какая-то логика отправки massage
        raise NotImplementedError("Это класс не должен инициализироваться.")
    
    
class EmailNotification(Notification):
    """Класс для отправки E-mail уведомлений для стандартных сервисов."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки уведомлений по E-mail'у."""
        standart_email_send(massage)


class EmailNotificationMyMail(Notification):
    """Класс для отправки E-mail уведомлений для mymail.com."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки уведомлений по E-mail'у."""
        my_mail_send(massage)  # не отработает для стандартного сервиса



class EmailNotificationBestMail(Notification):
    """Класс для отправки E-mail уведомлений для bestmail.com."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки уведомлений по E-mail'у."""
        best_mail_send(massage)  # не отработает для стандартного сервиса
    

```

Если нашей программой будет пользоваться новый разработчик, который плохо знаком с нашими наработками, то он вполне вероятно может использовать не тот объект для какого-то случая.

### Пример исправления:

Нам нужно поменять иерархию классов в приложении. Нужно завести отдельное семейство "неправильных Email" под одной абстракцией:

```python

from abc import ABC, abstractmethod


class Notification(ABC):
    @abstractmethod
    def send_notification(self, massage: str) -> None:
        """Метод будет отвечать за отправку пользователю уведомления."""
        # Будет какая-то логика отправки massage
        raise NotImplementedError("Это класс не должен инициализироваться.")
    
    
class EmailNotification(Notification):
    """Класс для отправки E-mail уведомлений для стандартных сервисов."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки уведомлений по E-mail'у."""
        standart_email_send(massage)


class NonStandartEmailNotification(Notification):
    @abstractmethod
    def send_notification(self, massage: str) -> None:
        """Оправка уведомлений для нестандартных Email сервисов."""
        # Будет какая-то логика отправки massage
        raise NotImplementedError("Это класс не должен инициализироваться.")


class EmailNotificationMyMail(NonStandartEmailNotification):
    """Класс для отправки E-mail уведомлений для mymail.com."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки уведомлений по E-mail'у."""
        my_mail_send(massage)  # не отработает для стандартного сервиса



class EmailNotificationBestMail(NonStandartEmailNotification):
    """Класс для отправки E-mail уведомлений для bestmail.com."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки уведомлений по E-mail'у."""
        best_mail_send(massage)  # не отработает для стандартного сервиса
    

```

Почему так лучше: будет проще понять, что у нас есть нестандартные Email сервисы и как их использовать.

# sol I d - Interface Segregation (Принцип разделения интерфейса)

### Суть принципа

Классы должны содержать только те методы, которые реально используются, и должны зависеть от абстракции, которая на 100% ими реализуется.

### Что будет если нарушить?

Ничего особо критичного не произойдет, но будет очень плохое разделение кода. То есть у вас будут классы, которых прописаны методы. которые им не нужны. Другие программисты это увидят и будут озадачены, потому что не будут понимать, а это так и надо, оно будет реализовано в будущем, почему так и т.п. Короче лишний код, плохая читаемость и т.п.

### Пример нарушения:

Давайте отвлечемся от наших уведомлений. Давайте про игры компьютерные пример. Давайте представим, что мы делаем игру Shooter (стрелялку) классическую. Нам нужно написать классы, которые описывают оружие, и мы пишем:

```python

        # Будет какая-то логика нанесение урона, если игрок попал
        raise NotImplementedError("Это класс не должен инициализироваться.")

	@abstractmethod
    def reload(self) -> None:
        """Метод будет отвечать за перезарядку оружия."""

		# Логика перезарядки AK-47

	    # Логика стрельбы пистолета

	def reload(self) -> None:
		# Логика перезарядки пистолета

    """Класс для оружия нож."""
```

Итак. теперь у нас есть ak-47, пистолет и нож, которые стреляют и перезаряж... СТОП! Что? Нож можно перезаряжать?! С ножа можно стрелять? Нет, ну ладно "стрельбы" здесь это просто нанесение урона, но КАК МОЖНО ПЕРЕЗАРЯДИТЬ НОЖ? Проблема в том, что класс Knife зависит от абстракции Weapon с методами shot() и reload(), т.е. по контракту он должен реализовывать данные методы, но он не будет использовать метод reload никогда, т.е. как раз идет нарушение принципа разделения интерфейсов.

### Пример исправления:

Нам нужно сделать для ближнего оружия в игре свою абстракцию, где будут только те методы, которые нужны для ближнего/холодного оружия:

Если вам нужно добавить ещё оружия, то сразу понятно, к какой категории его внести. Лучше масштабируемость и читабельность кода.

# soli D - Dependency Inversion (Принцип инверсии зависимостей)

### Суть принципа

Классы не должны иметь зависимости внутри методов напрямую так, что если нужно поменять использование одного класса на другой, то это нужно делать везде в классе, где он упомянет в коде. Такие связки должны быть заданы при инициализации класса через `__init__()`

### Что будет если нарушить?

Будет очень плохая заменяемость в коде. То есть у вас будет очень жесткая связка, что класс А использует в своих методах класс B. И когда вам нужно будет менять связку с A >> B на A >> C, то вам нужно будет именно менять это в коде везде, где до этого стоял B. А через неделю вам скажут, что надо теперь D, а ещё через неделю вернуть обратно B.

### Пример нарушения:

Давайте вернемся к нашему приложению с уведомлениям. Итак у нас там были разные способы отправки уведомлений. Каждый пользователь сам при регистрации указывает предпочитаемый способ. Но давайте представим, что мы только начали разрабатывать эту систему так, что у нас заложен пока что только 1 способ отправки:

```python

# Класс пользователя, который будет использовать отправку уведомлений:

        self.send_greetings()
		    
```

У нас есть какая-то регистрация пользователя и отправка уведомления на почту. Но мы развиваемся. Появилась задача, нужно сделать так, чтобы пользователь сам мог выбирать, как ему будут приходить уведомления (на почту, если региструется через сайт, можно в мобильное приложение, если он черех него и регистрируется, в ТГ, если ему так удобно). Все это надо заложить. Но сейчас наш класс User жестко связан EmailNotification.

Мы можем завести UserWithEmail, UserWithPush и т.п. Но это полное говно, так как будет дублирование кода.

### Пример исправления:

Нам нужно сделать возможность выбирать способ отправки уведомлений при инициализации класса User:

```python

from abc import ABC, abstractmethod


class Notification(ABC):
    @abstractmethod
    def send_notification(self, massage: str) -> None:
        """Метод будет отвечать за отправку пользователю уведомления."""
        # Будет какая-то логика отправки massage
        raise NotImplementedError("Это класс не должен инициализироваться.")


class EmailNotification(Notification):
    """Класс для отправки уведомлений по E-mail'у."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки уведомлений по E-mail'у."""
        # Логика отправки massage по E-mail
        pass


class PushNotification(Notification):
    """Класс для отправки push уведомлений в приложение."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки push уведомлений в приложение."""
        # Логика отправки massage d push уведомление
        pass


class SMSNotification(Notification):
    """Класс для отправки sms пользователю."""
    def send_notification(self, massage: str) -> None:
        """Метод отправки sms пользователю."""
        # Логика отправки sms пользователю
        pass


class User:
    def __init__(
	    self,
	    username: str,
	    email: str,
	    notification_service: Notification,
	    some_data: dict
	) -> None:
        # получаем какие-то данные от пользователя
        self.username = username
        self.email = email
        # теперь можно передать любой Notification
        self.notification_service = notification_service  
        self.some_data = some_data

    def send_greetings(self):
        # Оправка уведомления пользователю об регистрации
        self.notification_service.send_notification(
            massage=f"Hello, {self.username}, thanks for registration"
        )

    def registrate(self, username, email):
        # Тут какая-то логика регистрации пользователя в БД
        # после успешной регистрации посылаем пользователю уведомление
        self.send_greetings()


# Пример использования User теперь:
user_aboba = User(
	username = "Aboba",
	email = "Aboba@yandex.ru",  # будем использовать только для проверки почты
	notification_service = PushNotification()  # будет получать в приложение
	some_data = {}
)
user_guy = User(
	username = "guy",
	email = "guy@yandex.ru",  # будем использовать только для проверки почты
	notification_service = SMSNotification()  # будет получать по смс
	some_data = {
		"номер телефона": "8 800 555 35 35" 
	}
)


```

Почему так лучше: теперь нам просто добавлять новые способы отправки уведомлений пользователям, для этого буквально в коде User, где оно и используется не надо ничего менять. Мы зависим не от конкретной реализации класса EmailNotification, а семейства классов, которые объединены под абстракцией Notification, у наследников должен быть метод send_notification(), который отправит уведомление правильно, не важно какой это сервис (смс, Email, pysh, ТГ и т.п.). Это очень удобно, понятно и легко расширяется.
