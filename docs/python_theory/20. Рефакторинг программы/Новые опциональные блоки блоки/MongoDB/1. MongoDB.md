# Практическое задание

Вы разработаете небольшое приложения на Fast API, которое будет просто использовать MongoDB в качестве основной и единственной БД.

### Задание 1.

1. Вам нужно создать новый проект в IDE. 
2. Установите Fast API и Motor (это асинхронная библиотека/движок для управления MongoDB). 
3. Установите также саму СУБД MongoDB локально или сделаете для неё Docker образ.
4. Установите соединения для motor к MongoDB (почитайте [официальную документацию](https://motor.readthedocs.io/en/stable/tutorial-asyncio.html))

### Задание 2.

Мы сделаем БД для хранения данных о покупках в онлайн магазине. В основном мы просто добавляем и читаем данные. Очень редко модифицируем или удаляем. Почти никогда не анализируем.

1. Давайте сделаем простенькую архитектуру в БД. У нас будет 3 коллекции. Вам надо их создать.
2. В первой коллекции вы храним данные об наших зарегистрированных покупателях. В основном нам надо будет знать: имя, телефон, адрес доставки, количество заказов (будем выдавать VIP статусы)... Можете придумать свои данные для дальнейшего использования.
3. Во второй коллекции мы храним заказы. Нужно подумать, что мы будем сохранять о заказах: продукт, кому заказ, сколько уплачено, себестоимость, стоимость доставки для компании, когда создан заказ, когда доставлен... возможно вы придумаете ещё что-то.
4. В третьей коллекции сами товары. Нужно подумать, что будем хранить о них: наименование, описание, цена. какие-то параметры. Вы уже поняли, что у вас нет никакой схемы? Вы можете у дивана сделать и описание и габариты и вес, а у жесткого диска указать объём, скорость чтения/записи и все это в одной коллекции. Подумайте, как сделать так, чтобы это хранилось в одной коллекции, но потом эти данные было легко "распарсить", знать какие поля нам нужно достать у определенной записи из БД.
5. Коллекции должны быть связаны между собой, т.е. у заказа есть заказчик, пользователь нашего приложения, и в заказе есть продукт, который есть в коллекции "товары".

### Задание 3.

1. Сделайте по одной API для добавления, чтения, редактирования и удаления записи из каждой коллекции. Подумайте исходя из бизнес логики интернет-магазина, какие API реально нужны? Например: когда заказ доставлен, курьер ставит отметку о его завершении заказа. по факту он отправляет запрос на изменение определенной записи в БД, и у неё теперь есть время доставки.

### Задание 4.

1. Все готово к работе? 
2. Сделайте измерение скорости обращений к БД. На создание, поиск, редактирование и удаление данных. Вам нужно профилирование на стороне приложения.
3. Теперь создайте скрипт на Python, который будет создавать очень много post обращений на endpoint'ы вашего приложения для создания записей в БД. В идеале сделайте так, чтобы у вас получилось хотя бы по 1 Гигабайту данных в каждой коллекции.
4. Сделайте новые замеры. Это пока не проверялось, но по идее показатели скорости должны сильно упасть.
5. Подумайте над способами увеличения скорости запросов в БД. Посмотрите в сторону индексов в Mobgo.

### Задание 5.

Творческое задание. Если вы ещё "не наигрались". Попробуйте сделать аналитику на основе данных в MongoDB. Затем восаздайте такую же систему но через уже знакомый до этого PostgeSQL. Измеряйте скорость запросов на создание, чтение, изменение и удаление данных при определенном объеме данных >1 Гб или ещё больше. 

Что лучше подходит для аналитики? Что лучше для простого хранения больших объемов данных?
